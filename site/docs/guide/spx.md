# PHP-SPX

PHP-SPX — локальный профайлер PHP с интерактивными timeline, плоским профилем и Flame graph. Расширение
установлено во всех образах `php-fpm-8.2`–`php-fpm-8.5`, но само профилирование начинается только по явному
trigger-у. Пока trigger не задан, SPX не собирает отчёты.

> PHP-SPX предназначен для разработки, а не для production. Web UI раскрывает имена функций, пути и другие
> детали приложения, а создание отчётов расходует CPU и место в `/tmp/spx`. Не публикуйте домен разработки без
> внешней авторизации и выключайте расширение в образах, которые могут попасть в production.

## Включение расширений при сборке

Системный файл `~/.config/docker-cli/compose/.env` управляет составом сразу всех PHP-FPM-образов:

```dotenv
PHP_ENABLE_SPX=1
PHP_ENABLE_XDEBUG=1
```

Оба расширения включены по умолчанию. Значение `0` исключает соответствующее расширение из новых образов. После
изменения флага образы необходимо пересобрать без кеша и перезапустить:

```bash
docker-cli image:build --no-cache
docker-cli system:restart
```

Проверьте активный контейнер нужной версии:

```bash
docker exec docker-cli-php-fpm-8.2 php -m | grep -E '^(spx|xdebug)$'
docker exec docker-cli-php-fpm-8.2 php --ri spx
```

Флаги являются общими: отдельного значения для каждой версии PHP нет. Они влияют именно на сборку, поэтому простого
рестарта без пересборки недостаточно.

## Стили страницы настроек

При `docker-cli config:init` создаётся редактируемый файл:

```text
~/.config/docker-cli/compose/system/config/php-spx/settings.css
```

Его содержимое добавляется к штатному `main.css` PHP-SPX во время сборки всех PHP-FPM-образов. Поставляемые стили
располагают форму настроек и список отчётов в двух прокручиваемых колонках и скрывают заголовок страницы. Файл не
перезаписывается повторным `config:init` или `config:init --update`, поэтому локальные изменения сохраняются.

После редактирования CSS пересоберите образы без кеша и перезапустите сервисы:

```bash
docker-cli image:build --no-cache
docker-cli system:restart
```

## Профилирование страницы в браузере

1. Откройте панель SPX на домене профилируемого проекта:

   ```text
   https://web-my-project.<ваш-домен>/?SPX_KEY=docker-cli&SPX_UI_URI=/
   ```

   Запрос должен попадать в PHP через обычную точку входа проекта. SPX перехватит его до запуска приложения.
2. В панели включите **Enabled**, выберите метрики и оставьте тип отчёта `full`. Настройки сохранятся в cookie
   текущего домена.
3. В соседней вкладке загрузите страницу или API endpoint, который нужно исследовать.
4. Вернитесь в панель, обновите список отчётов и откройте нужную строку. Используйте timeline для порядка вызовов,
   Flame graph для поиска тяжёлых ветвей, а flat profile — для сортировки функций по выбранной метрике.
5. По окончании выключите **Enabled**, чтобы следующие запросы не создавали отчёты.

Без панели тот же сценарий можно запустить cookie или `curl`:

```bash
curl --cookie 'SPX_ENABLED=1; SPX_KEY=docker-cli' \
  "https://web-my-project.<ваш-домен>/catalog"
```

Ключ `docker-cli` и разрешение IP заданы для удобства локального окружения. Если домен доступен другим людям,
защитите его HTTP Basic Auth/сетевым фильтром либо задайте собственные `spx.http_key` и
`spx.http_ip_whitelist` в `config/php-fpm-<версия>/php/conf.d/zz-spx.ini`, затем перезапустите контейнер.

## Профилирование консольного скрипта

### Быстрый плоский профиль

Запустите команду в PHP-FPM-контейнере с `SPX_ENABLED=1`. Итоговый top функций появится в STDERR:

```bash
docker exec -it -e SPX_ENABLED=1 docker-cli-php-fpm-8.2 \
  php /home/user/projects/my-project/bin/console app:command
```

Для команды из интерактивного shell:

```bash
docker exec -it docker-cli-php-fpm-8.2 bash
cd /home/user/projects/my-project
SPX_ENABLED=1 php bin/console app:command
```

Прерванный через `Ctrl+C` процесс также печатает накопленный профиль. Для обновляемого в терминале профиля добавьте
`SPX_FP_LIVE=1`; этот режим перерисовывает терминал и заменяет обычный STDOUT/STDERR команды.

### Полный отчёт в Web UI

Чтобы сохранить CLI-профиль рядом с web-отчётами и изучить его в timeline/Flame graph:

```bash
docker exec -it \
  -e SPX_ENABLED=1 \
  -e SPX_REPORT=full \
  docker-cli-php-fpm-8.2 \
  php /home/user/projects/my-project/bin/console app:command
```

После завершения откройте панель SPX на любом проекте, обслуживаемом тем же PHP-контейнером. Отчёты лежат внутри
контейнера в `/tmp/spx` и удаляются при его пересоздании.

## Полезные параметры CLI

Параметры передаются переменными окружения:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `SPX_REPORT` | `fp` | `fp` печатает плоский профиль, `full` сохраняет отчёт для Web UI, `trace` создаёт текстовую трассировку. |
| `SPX_METRICS` | `wt,zm` | Метрики через запятую: время и память по умолчанию; например, `wt,ct,it,zm,io`. |
| `SPX_BUILTINS` | `0` | При `1` учитывает внутренние функции PHP, компиляцию и GC; отчёт становится заметно больше. |
| `SPX_DEPTH` | `0` | Максимальная глубина стека; `0` означает без ограничения. |
| `SPX_SAMPLING_PERIOD` | `0` | Период семплирования; полезен для долгих CPU-bound задач и уменьшения отчёта. |
| `SPX_FP_FOCUS` | `wt` | Метрика сортировки плоского профиля. |
| `SPX_FP_INC` | `0` | При `1` сортирует плоский профиль по inclusive, а не exclusive значению. |
| `SPX_FP_REL` | `0` | При `1` показывает относительные значения в процентах. |
| `SPX_FP_LIMIT` | `10` | Число строк в плоском профиле. |
| `SPX_TRACE_SAFE` | `0` | При `1` повышает сохранность trace при аварии ценой производительности. |
| `SPX_TRACE_FILE` | автоматически | Путь к trace-файлу для отчёта типа `trace`. |

Доступные метрики включают wall time (`wt`), CPU (`ct`), ожидание (`it`), память Zend (`zm`), RSS процесса
(`mor`), операции чтения/записи (`io`, `ior`, `iow`), объекты, GC, подключённые файлы и opcodes. Не включайте все
метрики без необходимости: каждая дополнительная метрика увеличивает накладные расходы и размер отчёта.

## Долгоживущие процессы и отдельный участок кода

Для worker-а или daemon-а обычно бесполезно профилировать весь срок жизни. Отключите автоматический старт:

```bash
SPX_ENABLED=1 SPX_REPORT=full SPX_AUTO_START=0 php worker.php
```

И ограничьте измерение нужной операцией:

```php
spx_profiler_start();

try {
    $job->process();
} finally {
    $reportKey = spx_profiler_stop();
}
```

Вызовы можно вкладывать. При `SPX_REPORT=full` `spx_profiler_stop()` возвращает ключ отчёта. Для различения заданий
можно во время активного профиля вызвать `spx_profiler_full_report_set_custom_metadata_str()` и передать строку
до 4 КБ, например JSON с идентификатором задания.

## SPX и Xdebug

Не запускайте профилирование SPX одновременно с пошаговой отладкой Xdebug: оба расширения инструментируют выполнение,
искажают время и увеличивают накладные расходы. Уберите cookie `XDEBUG_TRIGGER`/`SPX_ENABLED` либо переменную второго
инструмента и повторите измерение. Для production-сборки установите оба build-флага в `0`.

## Диагностика

- Пустая панель: убедитесь, что URL проходит через PHP entry point, проверьте `php --ri spx` и отключите
  `zlib.output_compression`.
- Код `403`: проверьте `SPX_KEY=docker-cli` и ограничения `spx.http_ip_whitelist`.
- Нет CLI-отчёта: переменная должна передаваться именно PHP-процессу; проверьте её через
  `docker exec ... env SPX_ENABLED=1 php ...`.
- Нет новых строк в Web UI: для CLI требуется `SPX_REPORT=full`; обычный `fp` выводится только в терминал.
- Недоступны RSS/I/O-метрики: в поставляемом FPM pool уже задан `process.dumpable=yes`; после локальной замены pool
  сохраните эту настройку.
- Отчёт слишком большой: уменьшите `SPX_DEPTH`, не включайте `SPX_BUILTINS`, сократите список `SPX_METRICS` или
  используйте `SPX_SAMPLING_PERIOD`.

### Ошибка `frame is undefined`

Это известное проявление несогласованного отчёта PHP-SPX: в потоке встречается событие завершения вызова без
соответствующего события начала. В upstream проблема зарегистрирована как
[issue #284](https://github.com/NoiseByNorthwest/php-spx/issues/284), но в релизе 0.4.22 ещё не исправлена.

В поставляемые образы включён защитный патч Web UI: такое событие пропускается, остальные корректные данные отчёта
продолжают загружаться. В консоли браузера при этом остаётся предупреждение. Поскольку повреждённое событие нельзя
восстановить, отдельные значения проблемного отчёта могут быть неполными. После обновления образов пересоберите их без
кеша, иначе Docker может оставить непатченным старый слой:

```bash
docker-cli image:build --no-cache
docker-cli system:restart
```

Если ошибка повторяется на уже пересобранном образе, удалите старый отчёт из `/tmp/spx`, создайте новый и начните с
метрик `wt,zm`, добавляя только необходимые. Это уменьшает накладные расходы и помогает отделить повреждение отчёта от
ошибки визуализации.

Полный перечень параметров и ограничения экспериментального расширения приведены в
[официальной документации PHP-SPX](https://github.com/NoiseByNorthwest/php-spx).
