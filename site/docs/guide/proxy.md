# ProxySQL и ProxyWeb

ProxySQL принимает подключения проектов к MySQL и PostgreSQL, направляет их в общий или выделенный сервер
нужного проекта и собирает статистику запросов. ProxyWeb — основной интерфейс для просмотра этой статистики и
служебных таблиц ProxySQL.

## Адреса и учётные данные

После `config:init`, `config:seed` и `system:start` доступны два интерфейса:

- `https://proxyweb.<BASE_HOST>` — ProxyWeb; используйте `PROXYWEB_ADMIN_USER` и
  `PROXYWEB_ADMIN_PASSWORD` из `~/.config/docker-cli/compose/system/.env`;
- `https://proxysql.<BASE_HOST>` — встроенный Web UI ProxySQL; используйте `PROXYSQL_WEB_USER` и
  `PROXYSQL_WEB_PASSWORD`.

ProxyWeb уже подключён к системному ProxySQL через его административный порт. Настраивать сервер в ProxyWeb
вручную не требуется. Учётные данные `PROXYSQL_ADMIN_*` предназначены для этого административного подключения,
а не для входа в ProxyWeb и не для подключения приложения к базе.

## Как направить проект через ProxySQL

Статистика появляется только для соединений, которые действительно проходят через ProxySQL. В конфигурации
приложения оставьте имя базы, пользователя и пароль проекта без изменений, а адрес замените на:

| СУБД | Host | Port |
| --- | --- | ---: |
| MySQL | `proxysql` | `6033` |
| PostgreSQL | `proxysql` | `6133` |

Например, для MySQL-проекта 1С-Битрикс достаточно заменить host подключения на `proxysql` и порт на `6033` в
`.settings.php`. Если приложение продолжает обращаться к `mysql:3306`, `postgres:5432` или непосредственно к
выделенному контейнеру, его запросы в статистику ProxySQL не попадут.

При добавлении, клонировании, изменении и удалении проекта docker-cli полностью пересобирает в ProxySQL:

- список общих и выделенных серверов;
- пользователей MySQL и PostgreSQL;
- правила маршрутизации по паре «пользователь — база/схема».

Старые проектные конфигурации без `hostname` считаются подключёнными к общим серверам
`docker-cli-mysql` и `docker-cli-postgres`. Менять их вручную только ради ProxySQL не нужно.

## Просмотр запросов в ProxyWeb

ProxySQL хранит не журнал каждого запроса, а агрегированную статистику по digest: одинаковые по структуре
запросы объединяются в одну строку, а литералы заменяются плейсхолдерами. Это позволяет найти частые и дорогие
запросы без сохранения каждого набора пользовательских данных.

1. Откройте `https://proxyweb.<BASE_HOST>` и войдите с `PROXYWEB_ADMIN_USER` /
   `PROXYWEB_ADMIN_PASSWORD`.
2. Убедитесь, что в селекторе сервера выбран **proxysql**.
3. Выполните нужный сценарий в приложении, подключённом к `proxysql:6033` или `proxysql:6133`.
4. Для MySQL откройте **stats → stats_mysql_query_digest**. Для PostgreSQL используйте соответствующую
   digest-таблицу из раздела **stats**, если она присутствует в используемой версии ProxySQL.
5. Используйте поиск и сортировку таблицы. Наиболее полезные поля:
   - `schemaname` и `username` — проектная база и пользователь;
   - `digest_text` — нормализованный текст запроса;
   - `count_star` — число выполнений;
   - `sum_time` — суммарное время;
   - `min_time` и `max_time` — минимальное и максимальное время;
   - `first_seen` и `last_seen` — границы периода наблюдения.
6. Для поиска главных источников нагрузки сначала отсортируйте по `sum_time`, затем отдельно проверьте
   большие `count_star` и `max_time`. Фильтр по `schemaname` или `username` оставит запросы одного проекта.

Чтобы измерить отдельное действие с чистого листа, откройте любую таблицу, разверните **SQL Query Editor** и
выполните:

```sql
SELECT * FROM stats_mysql_query_digest_reset;
```

После этого воспроизведите действие в приложении и заново откройте `stats_mysql_query_digest`. Сброс удаляет
накопленную агрегированную статистику MySQL для всего ProxySQL, поэтому не выполняйте его, если данные нужны
другим разработчикам.

Пункт **Query History** в ProxyWeb показывает историю команд, выполненных в собственном SQL-редакторе
ProxyWeb. Это не история запросов приложений; для анализа приложений нужна таблица digest из раздела **stats**.

## Встроенный Web UI ProxySQL

Интерфейс `https://proxysql.<BASE_HOST>` подходит для краткого обзора состояния и метрик самого ProxySQL.
Для поиска запросов проекта удобнее ProxyWeb: он позволяет открывать служебные таблицы, искать, сортировать и
просматривать длинный `digest_text`.

## Диагностика

- **Access denied для пользователя проекта.** Проверьте, что проект зарегистрирован, пароль совпадает с
  `project:show`, а приложение подключается к правильному порту.
- **В digest-таблице пусто.** Убедитесь, что приложение не обходит ProxySQL прямым подключением, и выполните
  реальный запрос после переключения host/port.
- **Проект попадает не в тот сервер.** Сверьте `username`, имя базы и `hostname` в `project:show`. Для старого
  конфига без `hostname` используется общий сервер соответствующей СУБД.
- **После обновления отсутствуют сервисы или переменные.** Выполните `docker-cli config:init --update --force`,
  `docker-cli config:init --migrate`, `docker-cli config:seed` и `docker-cli system:restart`.
