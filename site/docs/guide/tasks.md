# Пользовательские задачи

Задачи позволяют хранить переиспользуемые Bash-сценарии и описание их интерфейса в YAML. Docker CLI ищет файлы с расширением `.yaml` и `.yml` рекурсивно во всех подпапках `~/.config/docker-cli/actions/tasks`. Директория создаётся автоматически при первом обращении к задачам. Комплектные задачи хранятся в подпапке `core` и обновляются из ресурсов при `config:init --update`.

## Формат файла

```yaml
meta:
  schema: task
  version: 0.1
task:
  name: Демонстрационная задача
  code: demo.do-something
  type: shell
  context: project
  tags: [demo, maintenance]
  description: |
    Многострочное описание задачи.
    Оно отображается командой task:list.
  parameters:
    message:
      name: Сообщение
      type: string
      required: true
      tags: [text, input]
      description: |
        Текст, который будет напечатан.
        Описание параметра может быть многострочным.
    count:
      name: Количество
      type: integer
      min: 1
      max: 10
      required: true
    enabled:
      name: Включено
      type: boolean
      required: false
    format:
      name: Формат
      type: list
      required: false
      items:
        - { name: Обычный, value: plain }
        - { name: JSON, value: json }
  return:
    type: integer
    min: 0
    max: 255
    required: false
  action: |
    echo "{{ message }} $count $format"
```

Обязательные поля задачи: `name`, `code`, `type` и `action`. Сейчас единственный поддерживаемый тип задачи — `shell`. Поля `description`, `context` и `tags` опциональны. Теги задачи — список символьных кодов на латинице; допускаются также цифры, `.`, `_`, `:` и `-` после первой буквы. Задачи с `context: project` и тегом `project:init` доступны в панели как скрипты развертки при создании проекта. Содержимое опционального поля `tags` у параметров пока не валидируется и может содержать произвольные значения. Опциональное поле параметра `strict-types: true` запрещает очереди автоматически преобразовывать целое значение строкового параметра в строку.

Параметры поддерживают типы `string`, `integer`, `boolean` и `list`. Для `integer` можно задать `min` и `max`. `boolean` принимает значения `true` и `false` (также поддерживаются стандартные представления `1`, `0`, `yes`, `no`, `on`, `off`) и передаёт в окружение нормализованную строку `true` или `false`. Для `list` можно задать варианты `items` с полями `name` и `value`; само поле `items` опционально, поскольку в дальнейшем варианты смогут поступать из других источников на основании тегов. Если `items` отсутствует или пуст, текущее выполнение принимает любое переданное строковое значение списка. Поля параметра `name`, `description`, `required` и `tags` опциональны.

В полном выводе `task:list` варианты списка показываются отдельным от ограничений многострочным блоком в формате `value: name`. В режиме `--short` этот блок скрыт.

## Подстановка и окружение

В `action` значение параметра можно подставить конструкцией <code v-pre>{{ parameter-code }}</code>. Значения экранируются перед вставкой в Bash. Все переданные параметры также доступны как переменные окружения; дефисы в их кодах заменяются подчёркиваниями (`my-param` → `$my_param`). Скомпилированный скрипт исполняется с `set -Eeuo pipefail`.

Если `context: project`, проект определяется по текущей директории любой вложенности либо передаётся
явно через `--project`; рабочей директорией станет `document_root` зарегистрированного проекта. Для задач с тегом `project:init` используется корневая директория проекта, поскольку `document_root` может ещё не существовать до развертывания приложения. Код проекта автоматически доступен в `action` как переменная окружения `$project` и как шаблонная подстановка <code v-pre>{{ project }}</code>. При отсутствующем или falsy `context` используется `/tmp/.docker-cli`, которая создаётся автоматически.
Если `document_root` отсутствует, обычная проектная задача также запускается из корневой директории. Благодаря этому операции восстановления и удаления остаются доступны для проекта с незавершённой инициализацией.

## Просмотр и запуск

Полный список с описаниями и метаданными параметров:

```bash
bin/docker-cli task:list
```

Только краткие сигнатуры или только выбранные задачи:

```bash
bin/docker-cli task:list --short
bin/docker-cli task:list --task=demo.do-something,project.cleanup
```

Аргументы запуска передаются позиционно в порядке спеки либо как `name=value`:

```bash
bin/docker-cli task:run demo.do-something 'message=Hello world' count=2 format=plain
bin/docker-cli task:run --project=my-project demo.do-something 'Hello world' 2 plain
```

По умолчанию временный Bash-файл удаляется после выполнения. Опция `--no-delete` сохраняет его и выводит путь. Код завершения `task:run` совпадает с кодом завершения Bash-скрипта.

## Комплектные сценарии развёртывания

Комплектные задачи с тегом `project:init` отображаются в поле **Скрипт развёртывания** диалога добавления
проекта. Панель ставит выбранную задачу в очередь после `core.project.up`, поэтому к моменту её запуска проект
уже зарегистрирован, его базы созданы, а код проекта доступен в переменной `$project`.

### Laravel

Задача `core.project.init.laravel` не принимает параметров и выполняет следующие действия:

1. Проверяет наличие команды `laravel` в PHP-FPM-контейнере выбранной версии.
2. Если команды нет, устанавливает `laravel/installer` глобально командой Composer. Composer входит во все
   комплектные PHP-FPM-образы; если пользовательский образ его не содержит, задача завершается с ошибкой.
3. Создаёт стандартный скелет через `laravel new --no-interaction`, не перенося вложенный `.git`.
4. Записывает в `.env` соединение `mysql`, порт `3306`, hostname, имя базы, пользователя и пароль из
   `data.databases.mysql` конфигурации проекта.
5. Выполняет `php artisan migrate --force --no-interaction`.

Шаблон OpenResty для Laravel использует каталог `public`, `index.php` как индексный файл и направляет
динамические маршруты во front controller. После обновления шаблона пересоздайте конфигурацию и перезапустите
системные сервисы:

```bash
docker-cli config:init --update --force
docker-cli system:restart
```

Ручной запуск для уже зарегистрированного пустого проекта:

```bash
docker-cli task:run --project=my-project core.project.init.laravel
```

### 1С-Битрикс

`core.project.init.bitrix` требует параметр `edition`. Допустимые значения полностью соответствуют продукту
`bitrix` команды `bitrix:get-installer`: `start`, `standard`, `small_business`, `expert`, `business`.

```bash
docker-cli task:run --project=my-project core.project.init.bitrix edition=standard
```

Задача скачивает и распаковывает дистрибутив, запускает `play:run bitrix/setup`, затем удаляет каталоги
`bitrix/cache`, `bitrix/managed_cache` и `bitrix/stack_cache`.

### 1С-Битрикс24

`core.project.init.bitrix24` работает аналогично и принимает `business`, `enterprise` или
`enterprise_postgresql`:

```bash
docker-cli task:run --project=my-portal core.project.init.bitrix24 edition=enterprise
```

Playwright-сценарий распознаёт заголовки мастеров «1С-Битрикс24: Корпоративный портал» и
«1С-Битрикс24: Энтерпрайз» и выполняет для них одинаковую последовательность установки.

## Ошибки и незавершённая инициализация

Если init-задача завершилась до создания `document_root` (например, Laravel Installer не смог загрузиться),
обычные проектные задачи используют корень проекта как резервную рабочую директорию. Поэтому проект можно
удалить из панели или командой `project:down`, не исправляя вручную его конфигурацию.

Ошибки подготовки задачи записываются в её журнал до возврата кода `2`. В журнале очереди должна быть как
итоговая запись с кодом, так и конкретная причина — например, отсутствующий обязательный параметр или рабочая
директория.
